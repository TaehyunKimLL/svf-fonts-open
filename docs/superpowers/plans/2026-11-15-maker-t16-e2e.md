## Preset finding (measured during planning; the implementer re-confirms in Task 3 Step 1)

The planner ran the maker's own path on 004a449 (`inputkinds.plan_batch` + `jobs.Worker.run_job`; GowunBatang-Bold.ttf
with `ttf/gowunbatang/OFL.txt`, preset `dos-u-2bpp`, kinds `["precomposed"]`, sizes `[17]`, bpp `[2]`):

- argv: `mkfont.py SRC OUT --size 17 --cell 16 --clip-cell --ascent 15 --bpp 2 --unicode
  ascii,ksx1001-nohanja,AC37,B2CF,B584,C125,C2BA,D14A,D59D --report ...` (the preset's `--unicode` replaces the range's).
- The produced `GOWUN17A.SVF` and `svf/dos/GBATB17.SVF`: version 3, bpp 2, cell 16x16, ascent 15, count 3155, flags 5,
  the same `layout`, `glyphs`, `metrics` and `dy`; both 245,564 bytes; `cmp` reports the first difference at byte 813.
- `python3 tools/svf2to3.py OUT conv.svf --profile default` gives a file byte-equal to GBATB17.SVF.
- The step finished `done` with `identical_to: None`; the result was `written: ['svf/new/acc/GOWUN17A.SVF']`.

Why: `tools/build/build_faces.py` makes every `mkfont` face as `mkfont.py ...` then `svf2to3.py --profile default`;
the maker's mkfont route stops after `mkfont.py`, whose v3 layout is not the one `svf2to3` writes for the same profile.

**F1 is fixed by card t_df773bf5**, which lands before T16 Task 1: a face the maker bakes with mkfont was never
recognised as identical to the shipped face it reproduces, because `zipout`'s identity check compares bytes. After the
rebase, the step argv of a mkfont route may carry an extra tool (for example an `svf2to3.py` tail); the T16 tool
assertions are written so they hold either way (Task 1).

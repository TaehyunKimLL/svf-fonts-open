# CH582M port (YD-CH582M + SH1106) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A bare-metal CH582M image (`c/ports/ch582/`) that draws the `mono` profile on an SH1106 over I2C, built with the pinned
riscv32-esp-elf 16.1.0 and WCH CH583 EVT, verified on this host without hardware, and flashable with one documented command.

**Architecture:** The port follows the Pico port's shape (`display.h` contract, `profile_mono.c`, one driver, recording stubs
under `stub/`). Host verification is three layers in `c/ports/check` (driver byte stream, profile, a C model of the SH1106
fed by the whole image) plus an I2C-layer test; the stub cross-link and the real-SDK `make` image are measured into
`c/cross/SIZES.md` by `c/cross/build-all.sh`.

**Tech Stack:** C99 (gnu99 where the WCH headers are included), GNU make, POSIX sh, Python 3 (`-I`), riscv32-esp-elf-gcc
16.1.0, WCH CH583 EVT at `bd508ad`, wchisp 0.3.0.

**Spec:** `docs/superpowers/specs/2026-10-24-ch582-port-design.md` (commit e7274e9, card t_1a4449f3). Read it with this plan.

All commands run from the repository root (`<workdir>/svf-fonts-wt/ch582`, branch `ch582-port`). `OPT` is `$HOME/opt`.
The esp compiler is `$HOME/opt/riscv32-esp-elf-esp-16.1.0_20260609/bin/riscv32-esp-elf-gcc` (not on PATH).

## Global Constraints

- SVF v3 only; no change under `c/src/`, `c/include/` or the format ("the library as it is on main").
- Bare metal, polling, no interrupts of its own: no BLE stack, no `LIBCH58xBLE.a`, no FreeRTOS, no stdio, no `PRINT`, no sleep modes.
- No vendor IDE: a Makefile and a stock GCC; no MounRiver, no `.cproject`.
- No unpinned download: every fetched thing has a URL and a sha256, or a git commit checked before anything in the clone is used.
- Compiler: `riscv32-esp-elf-gcc` 16.1.0 (esp-16.1.0_20260609), `-march=rv32imac_zicsr_zifencei -mabi=ilp32`.
- SDK: github.com/openwch/ch583 commit `bd508ad7ceed48377619837051412a651952857f`, only `EVT/EXAM/SRC/` (plus the root `LICENSE`).
- wchisp v0.3.0: `https://github.com/ch32-rs/wchisp/releases/download/v0.3.0/wchisp-v0.3.0-linux-x64.tar.gz`, 883,953 bytes,
  sha256 `67e3d4eb0ffd3cc610d8927e3c3f452e2110531a3f14405dcaef87df219f200d`.
- RAM: 32 KB SRAM at `0x20000000`; stack `__stack_size = 2048`; the image's RAM total well under 8 KB. CodeFlash 448K at `0x00000000`.
- OLED: SH1106, I2C address `0x3C` (7-bit), 400 kHz, remapped pins **PB21 SCL / PB20 SDA** (`GPIOPinRemap(ENABLE, RB_PIN_I2C)`).
- The face array is generated at build time by `python3 -I c/bench/mkface.py ... --profile mcu-strict`, never committed.
- Library switches of the image: `-DSVF_NO_SCALE -DSVF_NO_STREAM -DSVF_LAYOUTS=SVF_LAYOUT_MCU_STRICT -DSVF_TARGETS=0x02`; no `SVF_SMALL`.
- No hardware is attached: nothing is flashed or run on a board; the README says "not yet tried on a panel".
- Downloaded trees are data: compile them, never run their scripts; Python that reads them runs with `-I`.
- Style: follow each file's existing style (tabs in the port sources and shell scripts, 4 spaces in `test_drivers.c`).
- Commits: message mentions card t_1a4449f3 and ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **No panel, wrong address, stuck bus** (the first thing a real board will meet): every I2C wait is bounded, STOP is
   always sent, `ch582_i2c_write` returns -1, the driver stops sending and the LED blinks at 2 Hz. Tests: Task 2
   (`test_ch582_i2c.c`, `errors()` in `test_drivers.c`), Task 4 (panel case C).
2. **The module is a variant** (an SSD1306 sold as SH1106 with RAM at column 0, or mounted upside down): the two
   `#define`s produce the documented stream and the compare notices a wrong offset. Tests: Task 2 (alternate build),
   Task 4 (negative build).
3. **The stub drifts from the real SDK** (a name or constant the host tests use that WCH spells or numbers differently):
   Tests: Task 2 (`ch582_sdk_values.c` against the real headers, `-fsyntax-only` of `i2c.c`/`disp_sh1106.c`), Task 4
   (`main.c` the same), Task 5 (the real build).
4. **The flash image is placed wrong** (`.highcode`/`.data` loaded at their RAM address, or a `.bin` spanning to
   `0x20000000`): wchisp programs PT_LOAD segments at `p_paddr`. Test: Task 5 (`image_sizes.py` refuses a loadable
   segment ending past `0x70000`; `.bin` at most 458,752 bytes).
5. **Stack or RAM overrun** in 32 KB with a 2048 B stack. Test: Task 5 (`stack-usage.py` peak of `main` at most 1,536;
   RAM total at most 8,192).

## Self-review notes (resolutions of the spec against the tree)

- **`-std=c99` for the port's files** cannot include the WCH headers (`core_riscv.h` has `asm volatile` in a static
  inline): port files use `-std=gnu99` against the real SDK; the host and stub builds stay `-std=c99`.
- **SDK source list**: a trial link on this host needed only `CH58x_gpio.c`, `CH58x_i2c.c`, `CH58x_sys.c` and the
  startup with `libISP583.a`; `.highcode` came to about 2.6 KB (vector table, `CH58x_sys.c`'s single `.highcode`
  section of 1,420 B that `--gc-sections` cannot split, and all 1,062 B of `ISP583.o`), not "a few hundred bytes";
  the RAM total stays under 8 KB.
- **wchisp layout**: the tarball has a top directory, so the normal unpack gives `wchisp-0.3.0/wchisp`, matching the
  Makefile default (not "flat"); `tool` gets `R_EXE` because wchisp has no `bin/`.
- **ch583 manifest inside a git tree** would make `git status` dirty: the installer excludes it in `.git/info/exclude`.
  The clone fetches the commit by hash (a `--depth 1` clone of `main` would miss it once `main` moves).
- **`CROSS` default** is the installed esp toolchain's path, not the bare prefix (it is not on PATH here).
- **Driver error path**: one build with a runtime failure point instead of a second build; the alternate-define build
  is the second build. An I2C-layer test (`port-check-ch582-i2c`) is added for Review Focus 1, so the full run prints
  42 OK lines, not 41.
- **Panel PNG** lands in the host-checks output directory (`<OUT>/sh1106-panel/ch582-mono.png`), not `c/build/screens`.
- **`--print-memory-usage`** reports RAM 100% (`.stack` sits at the top of RAM); the README uses `image_sizes.py`'s sum.

# MCU Ports (Pico, ESP32-C3, ESP32-S3: colour, grey, mono) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the Pico and ESP32 (C3 and S3) ports three build profiles each (`colour` RGB565, `grey` GRAY8, `mono`
MONO_PAGE), prove them on the host (recording stubs, profile tests) and end to end on emulated panels (rp2040js with
virtual SSD1306/SSD1327/ST7789; QEMU `esp_rgb`), and measure every kind on the Pico and both ESP32 chips.

**Architecture:** One table (`c/ports/profiles.txt`) maps a profile to kind, `SVF_TARGETS` bit, faces, driver and bus;
both CMake builds and `build-all.sh` read it. Each port has one `profile_<p>.c` (the drawing loop) and one
`disp_<driver>.c` (the panel) behind a four-symbol driver interface in `display.h`. The library does not change.
Host tests replay the drivers' byte streams against datasheet tables and the profiles' shows against
`tools/svfline.py`; the emulated screens run the real binaries and compare panel memory byte for byte.

**Tech Stack:** C99 `-Wall -Wextra -Werror`; CMake 3.28 (pico-sdk 2.3.1, ESP-IDF files read only); sh + awk; Python 3
(`tools/svfline.py`, Pillow 10.2.0, `unittest`); node v24 + rp2040js 1.4.0 (`node:test`); Espressif QEMU 9.2.2;
arm-none-eabi-gcc 15.2.1, riscv32-esp-elf-gcc 16.1.0, xtensa-esp32s3-elf-gcc 16.1.0 under `~/opt`.

**Spec:** `docs/superpowers/specs/2026-10-20-mcu-ports-design.md` (revision 4, f41a904) plus the plan-level
requirements of `.superpowers/sdd/2026-10-20-mcu-ports-design/plan-residuals.md`, which override the spec text where
they differ. Design history: `.superpowers/sdd/2026-10-20-mcu-ports-design/progress.md`.

## Global Constraints

- `c/src` and `c/include` do not change; `make -C c check` stays green after every task; `tools/test_c_renderer.py`
  unchanged. A needed library change is a separate card: stop and report.
- Every C file under `c/ports/` and `c/bench/` builds with `-std=c99 -Wall -Wextra -Werror` on the host and on its
  target compiler (Cortex-M0+ `-mcpu=cortex-m0plus -mthumb -Os`; C3 `-march=rv32imc_zicsr_zifencei -mabi=ilp32 -Os`;
  S3 `-mlongcalls -Os -DSVF_ESP32S3=1`). Selection macros are `SVF_TARGETS` bits or `-D` defines, never `SVF_T_*`
  enum names in `#if`.
- Profile constants (copied from the spec): colour fg `0xFFE0` bg `0x0010`, band `PORT_LCD_W x 24`, text x 8, band
  baseline 19, clear bands y = 24 i (i 0..9), text bands y = 16 + 28 i (i 0..4), `chain.missing_advance = 6`,
  scratch 90 bytes; grey 128 x 128 GRAY8, x 4, baselines 17 + 24 i, scratch 90; mono 128 x 64, x 0, baselines
  14 + 16 i (`svf_ascent(HGKEY6J)` = 14), threshold 128, scratch 32. Faces: colour and grey `svf/dos/PAPLG16.SVF` +
  `svf/dos/PAPLG18.SVF` (arrays `paplg16`, `paplg18`), mono `svf/iolo/HGKEY6J.SVF` (array `svf_face_data`).
- Pins: Pico SPI0 MOSI GP19 SCK GP18, CS GP17, DC GP16, RST GP20; Pico I2C0 SDA GP4 SCL GP5, address 0x3C. ESP32-C3
  MOSI 7 SCLK 6 CS 10 DC 2 RST 3; ESP32-S3 (`#if SVF_ESP32S3`) MOSI 11 SCLK 12 CS 10 DC 4 RST 5.
- Pico images use no stdio and no semihosting (no `printf`, no `pico_enable_stdio_*`, no BKPT): under rp2040js a
  BKPT fails the screen run.
- Tool paths (default `OPT=$HOME/opt`): `arm-gnu-toolchain-15.2.rel1`, `riscv32-esp-elf-esp-16.1.0_20260609`,
  `xtensa-esp-elf-esp-16.1.0_20260609/xtensa-esp-elf`, `qemu-esp-9.2.2-20260417-riscv32/qemu`,
  `qemu-esp-9.2.2-20260417-xtensa/qemu`, `rp2040js-1.4.0`, `pico-sdk-2.3.1`, `node-v24.13.0-linux-x64`. Python that
  reads downloaded files runs with `python3 -I`. Nothing under `~/opt` is deleted; the shared
  `qemu-esp-9.2.2-20260417/` directory is left alone.
- Artifacts (`.fb .ref .ppm .png .log`, build trees) live under `c/build/`, never in the repository.
- Every measurement is labelled emulated with emulator, machine, flags and what the number is (cycles; instructions,
  lower bound; CCOUNT-derived estimate). RGB565 and GRAY8 rows carry no budget.
- Commit trailer: the `Co-Authored-By` line the executing session's attribution reminder gives.

## Review Focus

1. `display_show` with a window off the panel (`y + rows > PORT_LCD_H`, mono `rows` not a multiple of 8, grey `rows`
   not a multiple of 4, `rows <= 0`, `buf NULL`): a reasonable driver sends nothing, not a wrapped or partial window;
   Task 3 and Task 4 `test_drivers.c` case `show_refused`.
2. Re-configuring an existing build directory with another `SVF_PROFILE`: the cache keeps the first value, so the
   user gets a stale image unless told; Task 5 (Pico) and Task 6 (ESP32 script-mode check) `configure_twice`.
3. A misspelt profile or display (`-DSVF_PROFILE=color`, `-DSVF_DISPLAY=ili9340`), and `PICO_SDK_PATH` neither `-D` nor
   in the environment: a configure error naming the choices, not a build failure later; Task 1 `test_profiles_cmake.sh`
   and Task 5 `configure_errors`.
4. An ELF of one profile run as another (`svf_pico_mono.elf` with `PROFILE=colour`): the runner must fail on the show
   count, not hang or report a green empty panel; Task 9 `test_pico_screen.mjs` `wrong_profile`.
5. A grey or colour string that does not fit its panel after an edit (the strings are data in two places): the
   self-check must fail before an image is built; Task 2 `screens.py --check` and `test_screens.py` `test_widths_fit`.

### Task 1: The profile table, its CMake parser, and `grey_pack_rows`

**Files:**
- Create: `c/ports/profiles.txt`, `c/ports/profiles.cmake`, `c/ports/grey_pack.h`, `c/ports/check/test_grey_pack.c`,
  `c/ports/check/test_profiles_cmake.sh`

**Interfaces — Produces:**
- `profiles.txt`: exactly the three rows of the spec ("One table, read by every build"), `#` comments allowed,
  whitespace-separated columns `profile kind targets faces driver_pico driver_esp32 bus_pico bus_esp32`.
- `profiles.cmake`, include mode: input `SVF_PROFILE` (required), `SVF_PORT` (`pico` or `esp32`), optional
  `SVF_GREY_KIND` (default the row's kind; only `GRAY8` accepted today, another value is
  `FATAL_ERROR "SVF_GREY_KIND <v>: only GRAY8 until card t_8e7da3c1"`); outputs `SVF_KIND`, `SVF_TARGETS_BIT`
  (`0x08`/`0x01`/`0x02`), `SVF_FACES` (a `;` list of paths under `svf/`), `SVF_DRIVER`, `SVF_BUS`, `SVF_GREY_KIND_DEFINE`
  (`SVF_GREY_KIND_GRAY8=1` for grey, empty otherwise). Unknown profile: `FATAL_ERROR "SVF_PROFILE <v>: choose one of
  colour, grey, mono"`; unknown port: `FATAL_ERROR "SVF_PORT <v>: pico or esp32"`.
- Script mode (`cmake -DSVF_PROFILE=p -DSVF_PORT=port -P c/ports/profiles.cmake`) prints one line
  `kind=<K> targets=<0x..> faces=<a,b> driver=<d> bus=<b>` (faces comma-joined), exit 0; errors exit non-zero.
- `grey_pack.h`: the function exactly as the spec gives it (signature
  `static inline size_t grey_pack_rows(const uint8_t *gray8, size_t stride, int w, int rows, uint8_t *out)`, the
  comment included).

- [ ] **Step 1: Write `test_profiles_cmake.sh`** (sh, exit 1 on a failure): for each of the 6 (profile, port) pairs the
  script-mode line equals the awk-derived line
  `awk -v p=$prof -v port=$port '$1 == p { ... }' profiles.txt` (column 5/7 for pico, 6/8 for esp32); `SVF_PROFILE=color`
  exits non-zero and stderr contains `choose one of colour, grey, mono`; `SVF_PORT=avr` exits non-zero; grey with

  8-bit grey, colour 5/6/5 replicated (`r << 3 | r >> 2`, `g << 2 | g >> 4`, `b << 3 | b >> 2`).

#define OLED_W 128
#define OLED_H 64
#define GREY_W 128
#define GREY_H 128

Stubs: `hardware/gpio.h` (`gpio_init`, `gpio_set_dir`, `GPIO_OUT`, `gpio_put`, `gpio_set_function`, `GPIO_FUNC_SPI 1`,
`GPIO_FUNC_I2C 3`, `gpio_pull_up`), `hardware/spi.h` (`spi0`, `spi_init`, `spi_set_format` with `SPI_CPOL_0 SPI_CPHA_0
SPI_MSB_FIRST`, `spi_write_blocking`), `hardware/i2c.h` as today; with `SVF_STUB_RECORD` the write and `gpio_put`
functions call the `svf_rec_*` hooks, without it they stay no-ops.
Driver behaviour (from the spec's layout table): ST7789 `spi_init(spi0, 32 * 1000 * 1000)` (*plan's call*), RST 0,
RST 1, then `0x01`, `0x11`, `0x3A 0x55`, `0x36 0x00`, `0x21`, `0x29`; a show is CS low, `0x2A` + 4 bytes, `0x2B` + 4,
`0x2C`, `rows * 480` data bytes, CS high; `display_565_bigendian = 1`. SSD1327: each command byte its own 2-byte
I2C write `{0x00, b}`; init `AE A0 51 A8 7F A1 00 A2 00 81 7F B1 F1 BC 08 A4 AF`; show: `15 00 3F`, `75 y y+rows-1`,
then `rows / 4` writes of 257 bytes (`0x40` + `grey_pack_rows` of 4 rows). SSD1306: today's init bytes; show: `21 00 7F`,
`22 y/8 (y+rows)/8-1`, then `rows / 8` writes of 129 bytes (`0x40` + 128 frame bytes). Never `nostop = true`.

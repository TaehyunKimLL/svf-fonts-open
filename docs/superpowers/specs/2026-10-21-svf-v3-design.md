## User decisions that rule this design (2026-10-21)

1. "SVF v3": a new format version, not a padded v2.
2. "잉크상자도 넣자. Spec에 있다고 꼭 기능을 써야하는 것은 아니다": ink-box glyph storage is in; a writer is free to
   store full cells.
3. "잉크상자 with 4byte 정렬 이런거 만들면 되는 거 아닐까?": the ink box and the 4-byte alignment are one encoding, the
   primary one. A full cell is the degenerate box.
4. "어차피 타겟마다 svf 만들어도 됨": a face may be written once per target; layout choices are header parameters and
   named writer profiles, and a reader handles every allowed value (or refuses what its build left out).
   "정렬 단위를 헤더에 기록해서 4바이트 정렬 이외의 정렬도 가능하게": the alignment units are recorded in the header, so
   alignments other than 4 bytes (up to 64) are possible. "각 렌더러는 모든 케이스를 지원하지 않아도 됨": no renderer
   has to support every case; each reader build declares the set it accepts and refuses the rest cleanly.
5. "V2배포 안했으니까 drop하고 v3 only로 진행해도 됨": v2 was never distributed. Readers read v3 only; v1 and v2 are
   refused cleanly; every shipped face is regenerated by a converter; the v2 code paths go.

## Why

- **Alignment.** The C speedups' word paths (merge, 1 bpp GRAY8 table) cannot use native loads on strict-alignment
  targets (Cortex-M0+, RP2350 Hazard3, ESP32-C3, maybe the S3) because v2 glyph data starts wherever the tables end:
  95 of 153 shipped faces have their glyph data at an offset that is not a multiple of 4 (HGKEY6J 4025, PAPLG18 24953,
  MARUS24 27197), and 30 have a stride that is not a multiple of 4. In v3 every table and every glyph record starts on a
  4-byte boundary (in the aligned layouts), so `src` of a piece merge is aligned by construction.
- **JSET bounds.** v2 infers the JSET's end from the next table's start (`jamoset.parse_svfn`, `svf__open_header`,
  `readLayout`); padding between tables breaks that. v3 names the JSET's offset and size.
- **Size.** Ink boxes with byte-aligned x shrink the glyph data of the shipped faces to 63.0 % (jamo sets 43.2 %,
  precomposed 76.9 %); whole files to 70.6-71.0 % under the aligned profiles, 68.6 % under the byte-tight one.
  Tight boxes (x to the pixel, which needs bit shifting in every reader) would give only 3 points more (60.0 %).

## Format

Little-endian throughout. Magic stays `SVFN` **(design call: every reader checks the version right after the magic, so a
new magic buys nothing and would break the "not this format, try another loader" path in ScummVM)**.

### Header (48 bytes, 12 words)

```
0  "SVFN"   4 u16 version (3)   6 u16 flags (bit 0 metrics table, bit 1 JSET, bit 2 marks at origin; others 0)
8  bpp (1, 2, 8)   9 layout: record and row units   10 layout: table unit and offset width   11 reserved (0)
12 u16 glyphs (1..65535)
14 cell width   15 cell height   16 ascent   17 dy_min (int8 <= 0)   18 dy_max (int8 >= 0)   19 reserved (0)
20 u32 metrics table offset      24 u32 glyph data offset        28 u32 glyph data size
32 u32 code point table offset   36 u32 JSET offset              40 u32 JSET size
44 u32 glyph offset table offset
```

Bytes 0..35 keep the v2 meaning of every field that survives, so the converter and the readers change the least. Bytes
9..10 (v2 shadow and code page, never read by a v2 reader) become the layout bytes; byte 11 is reserved, written 0 and
ignored **(design call: ignore rather than refuse, as v2 readers already did for both)**. `jamoset.py` stops carrying
shadow and code page through.

### Layout bytes (9 and 10): alignment units

Every unit is a power of two stored as its log2, 0..6 (1, 2, 4, 8, 16, 32 or 64 bytes):

```
byte 9   bits 0-2  REC  log2 of the record unit: every glyph record starts at a multiple of 2^REC from the file start
         bits 3-5  ROW  log2 of the row unit: each row of a record takes wb rounded up to 2^ROW bytes
         bits 6-7  0
byte 10  bits 0-2  TAB  log2 of the table unit: the code point table, metrics table, JSET, glyph offset table and glyph
                        data start at multiples of 2^TAB (the glyph data also at a multiple of 2^REC)
         bit 3     OFF  glyph offset table entries: 0 = u16 counting in units of 2^REC, 1 = u32 counting bytes
         bits 4-7  0
```

Constraints a reader checks (`SVF_E_LAYOUT` otherwise): `REC, ROW, TAB <= 6`; `ROW <= REC` (a row unit is relative to
the record start, so a larger row unit than the record's would not hold in the file); bits 6-7 of byte 9 and 4-7 of
byte 10 are 0. With u16 entries the glyph data reaches `65535 * 2^REC` bytes: 64 KB byte-tight, 256 KB at REC 2, 1 MB at
REC 4; the writer picks u32 when the data is larger (16 of the 153 shipped faces exceed 256 KB, GBATB47 alone 1 MB).
A reader build may accept only some of the valid values (its supported set, below) and refuses the rest with
`SVF_E_LAYOUT` before touching any table.

### Tables

- **Code point table** (offset 32): `glyphs` entries of `u32 code point, u32 glyph index`, sorted by code point, as v2.
  A code point listed twice resolves to its last entry, as v2.
- **Metrics table** (flags bit 0, offset 20): `glyphs` entries of 4 bytes `advance, bearing_x (int8), ink_w, dy (int8)`,
  as v2. The ink box below is storage only: advance, bearing and ink width keep coming from here and a reader must not
  derive them from the box **(design call: the box is in bytes and may be padded; the metrics are pixels and signed)**.
- **JSET** (flags bit 1, offset 36, size 40): the v2 JSET block unchanged (version 1, limits 12/12/24/16/16, at most
  11,681 bytes). The header size must equal what the block's counts give; a block that fails validation, or a size of 0
  with the flag set, leaves a plain face with `SVF_FACE_JSET_BAD`, as today. Without the flag both fields are 0.
  (Limits raised in Task 6b to 12/12/32/24/16, 12,321 B (user decision 2026-10-22).)
- **Glyph offset table** (offset 44): `glyphs + 1` entries; entry `i` is the start of record `i` relative to the glyph
  data offset, entry `glyphs` equals the glyph data size. Entries are non-decreasing. The length of record `i` is
  `off[i+1] - off[i]`, which a streamed reader needs to fetch a record in one read.
- **Glyph data** (offset 24, size 28): the records, in index order, each starting at its table entry.

Every table and the glyph data start at or after byte 48 and lie inside the file. The five offsets of bytes 20..47 are
multiples of `2^TAB`, the glyph data offset also of `2^REC`, every offset-table entry (in bytes) a multiple of `2^REC`,
and the data size as well; a reader checks these with one mask each and refuses otherwise (`SVF_E_LAYOUT`), since the
word and vector paths rely on them. With TAB 0 and REC 0 the file is byte-tight and the checks are vacuous.

### Glyph record

```
0  x0   left edge of the box, in BYTES of a cell row (pixel x0 * 8 / bpp)
1  y0   top row of the box in the cell
2  wb   box width in BYTES (0 = blank glyph, no rows follow)
3  h    box rows (0 = blank glyph)
4  phase bytes of padding (below), then h rows of rp bytes each, rp = wb rounded up to 2^ROW,
   then padding to the next multiple of 2^REC
```

- `x0 + wb <= pitch` and `y0 + h <= cell height`, where `pitch = (cell width * bpp + 7) / 8` as v2; a record that breaks
  either, or whose rows do not fit its table length, is refused (mapped: at open; streamed: when read, the cell is left
  blank and `SVF_E_RANGE` returned, the contract `svf_glyph` has today).
- Rows are bit-packed MSB first, the leftmost pixel in the top bits, exactly v2's row bytes cut at byte boundaries. Bits
  past the cell width in the last byte of the cell are written 0; readers mask them as today (`svf__mask_cell`).
- **x in bytes, not pixels** **(design call)**: a box's rows then drop into the cell with byte copies and byte/word ORs,
  no shifting, in every reader; the price against pixel-tight boxes is 3 points (63.0 % against 60.0 %).
- **Phase** **(design call)**: when `REC >= 2` and `ROW == 0`, a full-width record (`wb == pitch`) starts its rows at
  `4 + ((y0 * pitch) & 3)` instead of 4, so the rows lie at the same offset modulo 4 as their place in the cell
  (`cell + y0 * pitch`). A merge of such a piece into the cell is then one contiguous run whose source and destination
  share an alignment class, and the word loop of the C speedups can run it after a byte head. The phase is always
  modulo 4, whatever REC, because the word loops are 32-bit; a narrower record, or a file with `ROW > 0` or `REC < 2`,
  has phase 0. Cost: 1.1 points on the y-cropped profile (75.4 % to 76.5 %); nothing on the x-boxed profiles, whose
  records are rarely full-width.
- **Full cell** = `(0, 0, pitch, cell height)`; **y-cropped** = `(0, y0, pitch, h)`; **x-boxed** = `(x0, y0, wb, h)` with
  x0 and wb the byte span of the ink. These are writer policies on one record form; a reader does not know which was
  used. Row `r` of the record lies at `rec + 4 + phase + r * rp`; the reader computes `rp = (wb + (1 << ROW) - 1) &
  ~((1 << ROW) - 1)` once per record. A separate fixed-stride full-cell mode is **not** kept in v3 **(design call)**: it would be a second glyph path
  in every reader for a 4-byte-per-glyph saving (the offset table) that no shipped face needs, and v2, which was that
  mode, is being dropped.
- **Blank glyph**: `wb == 0` or `h == 0`, a 4-byte record (padded to `2^REC`); the reader clears the cell.

What the numbers decide:

- **4-byte rows do not serve the MCU faces** **(design call, against the "mcu-strict = 4-byte rows" first guess)**: a
  16 px 1 bpp row is 2 bytes, so padding rows to 4 doubles them (HGKEY6J 101 % of v2), and the renderer's word loops run
  along a contiguous run (a whole cell or a full-width piece), not along one row. Row alignment 4 stays an allowed value
  for a target that wants to load a row as a word (a 2 bpp 32+ px or 1 bpp 64+ px face, or a later SIMD row blit); no
  profile picks it today.
- The aligned-record padding costs 0.4 % of v2 and 1.5 points against byte-tight records (64.5 % against 62.1 % on
  x-boxed data) — the "dos/x86" and "wasm" profiles take the byte-tight form, nothing else differs.
- u16 offsets halve the table (1.8 % of the data) and fit every MCU face; the writer falls back to u32 per file.
- **Larger record units are cheap, larger row units are not.** Record 8 costs 1.8 points over record 4 (64.8 % against
  63.0 %), record 16 costs 5.6 (68.6 %), record 32 costs 13 (76.1 %; HGKEY6J back at 100 %). Rows of 16 bytes cost
  2.4x the v2 data (238 %) because a 16-18 px row is 2-5 bytes; only a wide face stays sane (GBATB47 111 %). A vector
  profile should therefore take record 16 (or 32) with byte rows and load 16 bytes across a contiguous run of rows, not
  one row per vector; row 16 is a choice for wide title faces only. The format allows both; the SIMD card measures.

`dos` and `wasm` are one layout under two names, so a map or a build script can say which it means. A face's bytes
differ between profiles; its pixels do not (the identity test below). Any other combination of units is a valid file
that the default reader build accepts; the profiles are the named ones the writers expose. Alignment larger than 16 has
no user today; 32 and 64 are allowed so a cache-line or DMA-burst layout needs no new version.

## Reading a glyph

Lookup: code point table (binary search, as today) gives the glyph index `g`; `off[g]` (one u16 or u32 load, times 4
for u16 in an aligned file) gives the record; the record header gives the box. That is one load more than v2's
`g * stride` and no multiply; the M0+ pays about the same.

The C renderer expands a record into the caller's cell: `memset(cell, 0, stride)`, then for each of `h` rows copy
(`svf_glyph`) or merge (`svf_compose`, max rule) `wb` bytes from the record into `cell + (y0 + r) * pitch + x0`. A
full-width record is one run of `pitch * h` bytes (the phase makes it word-loopable). Everything after the cell — every
blit, the composed-syllable cache (cell-sized entries, `svf_chain_cache`), scaling, marks, dy — is untouched, which is
how byte identity with the Python reference is kept by construction. Skipping the blank rows of the cell in the blits
with the box's `y0, h` is a later optimisation, not this card. A streamed face reads the record in one `read_all` of
`off[g+1] - off[g]` bytes (or through the block cache as today, the record's bytes being contiguous), into the scratch
half of the cell for a merge; the cache block rule "cut at the end of the glyph data" stays. The streamed tables buffer
grows by the offset table (2 or 4 bytes a glyph: 4.9 or 9.8 KB for a 2446-glyph face on DOS, 0.6 or 1.1 KB for a jamo
set).

### Supported sets: what a reader build accepts

No reader has to read every valid v3 file (user). Each reader declares its **supported set** over the layout parameters
(REC, ROW, TAB, OFF) and refuses a file outside it with `SVF_E_LAYOUT` before reading any table, naming the parameter
in its message where it has one (`svfdump`, the picker, ScummVM's warning). A writer profile exists for every reader's
set (the table above), so every target has a producible face. The sets:

| reader | set | how it is chosen |
|---|---|---|
| C library, default build (host, DOS, WASM, M33, Hazard3, C3, S3, the Pico/ESP32 colour and grey profiles) | every valid value: units 1..64, u16 and u32 | `SVF_LAYOUTS` unset |
| C library, M0+ P1/P2 and AVR builds | exactly the `mcu-strict` pair (REC 4, ROW 1, TAB 4; u16 and u32) | `SVF_LAYOUTS=SVF_LAYOUT_MCU_STRICT` |
| `svfline.py`, `jamoset.parse_svfn`, `svfdump`, the converter | every valid value | tools: they are the reference and the proof of identity, so they must read whatever any writer emits; they are not budgeted |
| `facecheck.py` | reads no SVFN header itself today (it hashes files against the manifest); if it gains a header check it uses `jamoset.parse_svfn`, every value | |
| WASM picker | the C default build: every value | |
| ScummVM `readLayout` | every value **(design call: it reads faces from any pack, so a narrow set would only turn a bad pack into a warning the user cannot act on; its glyph path expands into a cell and has no word loop that cares)** | |

The C library's switch, in the way `SVF_TARGETS` chooses output kinds **(design call)**:

- `SVF_LAYOUTS`: unset (every valid value) or a list of accepted (byte 9, byte 10) pairs as a compile-time constant;
  `SVF_LAYOUT_MCU_STRICT`, `SVF_LAYOUT_TIGHT` (dos/wasm) and `SVF_LAYOUT_SIMD16` are named in `svf.h`. With one pair the
  three units and the offset width fold to constants; with several the open keeps the file's shift counts in the face
  struct (3 bytes and a flag; the 64-byte face budget holds). `svf_layouts()` returns the build's set so a port can
  print it next to the error.
- Refusal happens in `svf__open_header` right after the version check: `SVF_E_LAYOUT` (appended to `svf_err` after
  `SVF_E_ARG`, named in `svfdump.c` and `picker.js`'s `ERR` table). A refused face holds nothing, as a failed open does
  today, so nothing is misread.
- **Cost of general units against fixed 1|4** (estimate at `-Os` on the M0+): the general form keeps a shift count per
  unit and uses `(n + m) & ~m` with `m = (1 << k) - 1` where a fixed form uses a constant mask: about 4-6 instructions
  per use at three uses (offset entry scale, row pitch, record padding check) plus the open-time mask checks, about
  +40..+80 B over the fixed form. A one-pair `SVF_LAYOUTS` gives all of it back, which is what the M0+ build does.
- `SVF_E_LAYOUT` is appended to `svf_err` (after `SVF_E_ARG`), named in `svfdump.c` and `picker.js`'s `ERR` table.
- No `SVF_READ_V2`: the v2 path is removed, not switched.

### Refusing other versions

Every reader checks `version == 3` right after the magic. The C renderer returns `SVF_E_VERSION` for 1 and 2 (the
comment and `svfdump` text say "version 2 is not read since v3; convert with tools/svf2to3.py"); `jamoset.parse_svfn`
and `svfline.Face` raise `ValueError("SVFN version 2: convert with tools/svf2to3.py")`; ScummVM's `readLayout` sets
`kMinVersion = kMaxVersion = 3` and keeps its warning "font version %d is not supported by this build"; the picker shows
the error name. Nothing reads a v2 field as a v3 one: a v2 reader given a v3 file already refuses it (`rd16(4) != 2`,
`kMaxVersion = 2`, `version != VERSION_CMAP`), measured today.

## Code size (estimates; the builder measures with `c/cross/build-all.sh` and `check-sizes-md.sh`)

- **M0+ P1/P2** (5,674 B today, limit 8,192, +136 B planned by the speedups), built with
  `SVF_LAYOUTS=SVF_LAYOUT_MCU_STRICT`: the fixed-stride glyph access and the JSET end inference go (about -60 B); the
  offset table lookup (u16 and u32), record header decode, range and alignment checks with constant masks, and the
  row-wise expand and merge come (about +200..+320 B at `-Os`). Net about +140..+260 B, so about 5.9 KB before the
  speedups' +136: about 2.1 KB under the limit. The general-unit arithmetic (+40..+80 B) is not in this build; a
  default build on the M0+ (P3, P3g, no budget) carries it.
- Host, DOS, WASM, M33, Hazard3, C3, S3: the same delta within a few hundred bytes; no budget bears on them.
- AVR bench build (31,302 of 32,256 B flash): the same +150..+260 B leaves about 700 B; the Arduino port (26,442) has
  room. The AVR reads records through `pgm_read_byte` as today; no word loop there.
- Python readers: `parse_svfn` shrinks (no JSET inference) and gains a record expander (about 25 lines); `svfline.Face`
  takes its glyphs from `parse_svfn` and does not change beyond the version check.

## dy, pieces and marks with ink boxes

- **dy** is unchanged: the record is expanded into the stored cell, and dy moves the whole cell at draw, so ink that dy
  carries outside the cell is drawn as before. The box's `y0` is a position inside the stored cell and has nothing to
  do with dy; `dy_min`/`dy_max` keep their rules and the `SVF_FACE_DY_IGNORED` status.
- **JSET pieces** are records like any glyph (x-boxed pieces are what makes the jamo sets 43 %). A syllable is composed
  by merging each piece's box into the cleared cell with the max rule; a piece must still not carry a dy
  (`jamoset.py check` refuses one). The composed cell, its advance (JSET advance or cell width) and the syllable cache
  do not change.
- **Combining marks** (flags bit 2): unchanged; the mark's origin comes from its metrics bearing, not from the box.
- **Cell-sized scratch** stays the caller's requirement (`svf_chain_scratch_bytes` unchanged).

## Converter and regeneration

`tools/svf2to3.py IN OUT [--profile P]` (new, about 120 lines): reads a v2 file with the last v2-capable
`jamoset.parse_svfn` (kept inside the converter as `_parse_v2`, not in `jamoset.py`), computes each glyph's byte box,
writes v3 through the new `jamoset.write_svfn(..., profile=...)`. `--check` renders every glyph and composed syllable of
IN and OUT through `svfline` and fails on any difference. `svf/` is regenerated in the `default` profile in one commit;
`manifest/` gains `baseline-<date>-v3.tsv` next to the 2026-10-19 baselines (which stay as the v2 record). The bench
embeds (`c/bench/mkface.py` arrays of HGKEY6J, PAPLG16, PAPLG18, MARUS24) are regenerated in `mcu-strict`.

## Design calls, collected

1. Magic unchanged; bytes 9-10 become the layout bytes; byte 11 reserved and ignored.
2. Alignment units as log2 (1..64 bytes) for records, rows and tables in bytes 9-10, `ROW <= REC`, offsets u16 in record
   units or u32; out-of-range values, non-zero reserved bits and inconsistent offsets refused with `SVF_E_LAYOUT`.
3. Box x and width in bytes, not pixels (3 points of size for shift-free readers).
4. Phase padding for full-width records in aligned files, so contiguous merges can run words after a byte head.
5. No fixed-stride full-cell mode; `full` is a writer profile of the one record form.
6. The record carries its own box header (not a side table), so a streamed read is one read per glyph.
7. The reader expands into the cell; nothing downstream of the cell changes in this card.
8. `mcu-strict` uses byte rows, not 4-byte rows (measured: 4-byte rows cost 101 % of v2 on HGKEY6J and help no word
   loop the renderer has); a vector profile takes record 16 with byte rows (68.6 %), not 16-byte rows (238 %).
9. Each reader declares a supported set; the C library's is `SVF_LAYOUTS` (like `SVF_TARGETS`), every value by default,
   the one `mcu-strict` pair on M0+ P1/P2 and AVR; the Python tools, the picker and ScummVM read every value;
   `SVF_E_LAYOUT` appended to `svf_err`.
10. One shared packer for every Python writer; the converter keeps the only v2 parser.
11. Mapped records validated at open; streamed records when read.
12. A short fuzz run over the new record parser.
